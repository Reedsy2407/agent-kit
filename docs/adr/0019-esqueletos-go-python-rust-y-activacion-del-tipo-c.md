# 0019. Esqueletos de Go, Python y Rust y activación del tipo C

Estado: aceptada (2026-10-29). Complementa los ADR 0016 (esqueletos del tipo B), 0014 (presets de sello) y 0018 (tipo C como guía de decisión).

## Contexto
El tipo C tenía guía de decisión pero no se podía instalar ni daba un punto de partida que compilara. Como en el tipo B, un esqueleto sin verificar sería justo lo que el kit combate; y como el entregable es un binario o paquete, sus problemas propios (señales, permisos de archivo, entrada no confiable, varias plataformas, distribución con integridad) tienen que estar en el código de partida y no solo en la guía.

## Decisión
- **Un contrato, tres implementaciones.** `types/C/esqueletos/CONTRATO.md` es la única fuente de verdad del comportamiento (se instala como `kit/CONTRATO-ESQUELETOS.md`); los README de cada esqueleto lo citan y solo dicen lo propio de su lenguaje. CLI con `version`, `check-config` y `run` (daemon, o `--once`), códigos de salida 0 a 4 documentados, resultados en stdout y diagnósticos en stderr, `--json` para máquinas; configuración `clave=valor` validada al arrancar (falla pronto, con número de línea) con comprobación de permisos donde el sistema los expone (en Windows no se comprueban y se declara); entrada no confiable con límite de tamaño y plazo; registro JSON estructurado sin secretos; apagado ordenado que **drena** la vuelta en curso. El formato `clave=valor` (y no JSON o TOML) es deliberado: Rust no trae lector de JSON en la biblioteca estándar y el contrato debe ser idéntico sin dependencias.
- **Solo biblioteca estándar en tiempo de ejecución** en los tres (`go.mod` sin `require`, `dependencies = []` en `pyproject.toml`, `Cargo.toml` sin dependencias). Una prueba del kit lo comprueba.
- **Go** (`types/C/esqueletos/go/`): `log/slog`, `os/signal`, módulo con `internal/`. `gofmt -l` sale con 0 aunque haya diferencias y el sello solo mira el código de salida, así que una prueba (`internal/formato`, con `go/format`, que es el propio gofmt) hace cumplir el formato con `go test` en cualquier sistema; la integración continua además corre `gofmt -l` (falla si no está vacío), `go vet`, `go test -race` y `govulncheck`.
- **Python** (`types/C/esqueletos/python/`): `unittest` (sin añadir `pytest`), `logging` con un formateador JSON, `pyproject.toml` con punto de entrada instalable y `requires-python = ">=3.11"`; integración continua con `ruff check`, `ruff format --check` y `pip-audit`. La espera entre vueltas se corta en tramos de 0,2 s porque en Windows un manejador de señal no interrumpe una espera larga.
- **Rust** (`types/C/esqueletos/rust/`): edición 2024, `Cargo.lock` versionado, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` y `cargo audit`. **Excepción justificada:** la biblioteca estándar de Rust no maneja señales. En vez de una dependencia, `src/senal.rs` declara a mano `signal` (POSIX) y `SetConsoleCtrlHandler` (Windows) y su manejador solo escribe un `AtomicBool`. Es el único `unsafe` del esqueleto: `Cargo.toml` fija `unsafe_code = "deny"`, solo ese módulo lo permite y una prueba del kit falla si aparece `unsafe` en otro archivo. Se aceptó frente a una dependencia porque son dos funciones del sistema estables, con el mínimo de superficie; la alternativa (una biblioteca de señales) queda documentada en el README como cambio con su ADR.
- **Integración continua y publicación de ejemplo, no automatización del kit.** Cada esqueleto trae `ci.yml` (matriz Ubuntu, Windows y macOS; versiones de las acciones y de las herramientas fijadas; solo lectura) y `release.yml` (un artefacto por plataforma, o uno solo si el paquete es de Python puro, y `SHA256SUMS`; sin secretos ni firmas inventadas). Lo que queda manual está dicho en cada README: subir al canal de distribución, publicar las sumas por un canal distinto, firmar si se decide y probar `version` y `check-config` en cada plataforma declarada. Ninguno se ejecuta dentro del kit (excepción del ADR 0016 sobre `.github/workflows`).
- **Presets por tipo.** `infra/presets.mjs` separa los presets del tipo C (`go`, `python`, `rust`) de los de A y B: el `python` del tipo B (pytest) y el del tipo C (ruff y unittest) son presets distintos con el mismo identificador, así que las funciones reciben el tipo. Cualquier otro identificador se rechaza con un mensaje que lista los válidos del tipo. Cada preset es una lista de comandos del sello (Go: `go vet`, `go test`; Python: `ruff check`, `ruff format --check`, `unittest`; Rust: `cargo fmt --check`, `cargo clippy`, `cargo test`). Sin preset ni `kit.checks` el sello se niega, como en el tipo B. `guard-shell` exige `timeout` en estos comandos.
- **Instalador y fichas.** `--tipo C` se acepta; `types/C/manifest.json` pasa a `disponible` (el catálogo sigue pendiente: el tipo C continúa «en construcción» en la documentación). Instala el núcleo, las dos skills de decisión (no el catálogo del tipo B), la guía, la plantilla de viabilidad, los ejemplos, el contrato y, **solo si la ficha declara `kit.preset`**, el esqueleto de ese lenguaje y sus líneas de `.gitignore`. La ficha del tipo C no asume proveedor: `despliegue.proveedor` y `distribucion.proveedor` quedan vacíos para que el humano los declare.
- **Verificación repetible.** `node types/C/esqueletos/verificar.mjs <go|python|rust>` instala el esqueleto en una carpeta temporal, corre el sello, los extras del stack, la construcción, trece casos del contrato del CLI y, en sistemas POSIX, el daemon con SIGTERM. Registro con fecha, versiones y límites en `types/C/esqueletos/VERIFICACION.md`; un preset solo figura como verificado si ese registro lo recoge. No forma parte de `node --test`.
- **Entorno del verificador (0.9.1).** Una terminal abierta antes de instalar Go o Cargo no los tiene en el PATH, y un equipo con software de seguridad que inspecciona el TLS hace que `pip` no valide PyPI (usa su propio paquete de certificados y respeta `CURL_CA_BUNDLE`). `verificar.mjs` (con `entorno.mjs`) añade al PATH de sus comandos las carpetas habituales si existen y faltan, y solo si `pip` falla **por el certificado** exporta a un PEM temporal fuera del repositorio los certificados que el sistema operativo ya confía (`tls.getCACertificates`, Node 22.15 o superior) y repite la prueba con `PIP_CERT`, `REQUESTS_CA_BUNDLE` y `SSL_CERT_FILE`. No sobrescribe lo que el humano definió, no actúa si el fallo es otro y nunca desactiva la verificación (`--trusted-host`, `PIP_NO_VERIFY`, `verify=False`: prohibidos y vigilados por una prueba). Añade `pip install .` en un entorno virtual temporal y la comprobación de `herramienta version`.
- **Material privado del tipo C** en `types/C/casos-privados/` (ignorada por git, también en `PROHIBIDOS` del exportador): una prueba comprueba que sigue ignorada, que no se versiona y que el instalador no la copia a ningún proyecto.
- **El exportador distingue un correo de una versión fijada.** Una cadena como `herramienta@v1.9.0` (así se fijan `go run` y las acciones) ya no cuenta como correo: la última etiqueta de un correo debe ser alfabética.

## Alternativas descartadas
| Alternativa | Por qué se descarta |
|---|---|
| Configuración en JSON | Rust no tiene lector de JSON en la biblioteca estándar; haría falta una dependencia o un lector propio en uno solo de los tres, y el contrato dejaría de ser idéntico |
| `signal-hook` o `ctrlc` en Rust | Una dependencia de producción para dos funciones del sistema; el costo (revisión de la cadena de suministro, ADR 0004 del kit) pesa más que ese `unsafe` acotado y probado |
| `pytest` en el esqueleto Python | Añade una dependencia de desarrollo; `unittest` basta y mantiene el esqueleto sin nada que instalar |
| Un solo esqueleto «agnóstico» con tres carpetas de código sin contrato | Tres comportamientos distintos; el contrato común obliga a que las diferencias sean de idioma y no de semántica |
| Que el sello ejecute `gofmt -l` | Sale con 0 con diferencias; el sello solo mira el código de salida. Se resuelve con una prueba que usa `go/format` |
| `go test -race` en el sello | Exige cgo, es decir, un compilador de C en cada máquina; se deja a la integración continua |
| Empaquetar el esqueleto Python como binario único | Añade un empaquetador de terceros; si hace falta binario único para usuarios sin Python, la señal es evaluar otro lenguaje (está en «qué no construir todavía») |
| Instalar siempre los tres esqueletos | Ruido de lenguajes que el proyecto no eligió; solo se instala el declarado en `kit.preset` |

## Consecuencias
- Un proyecto nuevo del tipo C arranca con algo que compila, se prueba, tiene el contrato de CLI y daemon y se puede publicar con sumas; el sello deja de avisar de preset sin verificar.
- Tres implementaciones que mantener al subir de versión (Go, Python, Rust, ruff, acciones). Se repite `verificar.mjs` y se actualiza `VERIFICACION.md`.
- **Lo que no se verificó queda dicho** en `VERIFICACION.md`: el apagado por señal de punta a punta en Windows (Node no envía SIGTERM allí), `go test -race` (sin compilador de C), `pip-audit` (TLS de PyPI no verificable desde la máquina), `pip install .`, `cargo audit` (no instalado), Python 3.14, Linux y macOS (el código `cfg(unix)` de Rust no se compiló) y los flujos de integración continua.
- La puerta de uso responsable (ADR 0018) sigue siendo una regla de juicio; los esqueletos no la implementan porque son herramientas neutras de ejemplo.

## Sin hacer
Catálogo de problemas del tipo C y sus notas por lenguaje (etapas C3 y C4), fichas con proveedor de distribución concreto, firmas de artefactos, empaquetado nativo por plataforma (instaladores) y un esqueleto de librería (sin binario).
